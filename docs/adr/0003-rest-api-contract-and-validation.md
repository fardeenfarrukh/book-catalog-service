# ADR-0003: REST API Contract and Validation

## Status

Proposed — pending review

## Date

2026-10-28

## Owner

Project contributor

## 1. Context

The Book Catalog Service exposes HTTP endpoints for creating, retrieving, searching, and updating book records. A consistent API contract makes the service easier to use, test, and maintain.

Book records contain an ID, title, author or authors, ISBN, genre, price, publication year, and inventory quantity. Requests must be validated so that invalid data does not enter the catalog.

Inventory requires particular care because quantities must never become negative. The API must also distinguish invalid input from a book that does not exist.

## 2. Decision Drivers

- Use predictable HTTP methods and resource-oriented URLs.
- Validate incoming data before accepting changes.
- Return appropriate HTTP status codes for successful and unsuccessful requests.
- Keep book IDs stable when a record is updated.
- Ensure inventory quantities are non-negative integers.
- Make the API straightforward to test and document.
- Keep the initial contract focused on the required project operations.

## 3. Alternatives Considered

### Option A: Resource-Oriented REST-Style Endpoints

Use HTTP methods such as `GET`, `POST`, `PUT`, and `PATCH` against book resource URLs.

**Advantages**
- Uses familiar HTTP conventions.
- Makes endpoint behavior easier to understand.
- Supports clear separation between retrieving, creating, and updating resources.
- Works naturally with automated API tests.

**Disadvantages**
- Requires consistent decisions about request formats, validation, and response codes.
- Partial updates and full-resource updates need clearly defined behavior.

### Option B: Action-Oriented Endpoints

Use URLs that describe operations, such as `/addBook` or `/updateInventory`.

**Advantages**
- Can make individual operations explicit.
- May be convenient for a very small internal interface.

**Disadvantages**
- Can lead to inconsistent endpoint naming as the API grows.
- Does not use standard resource-oriented HTTP conventions as consistently.

### Option C: Minimal Validation

Accept most request data and rely on callers to provide valid values.

**Advantages**
- Reduces initial validation code.

**Disadvantages**
- Allows malformed or inconsistent records into the catalog.
- Makes error handling less predictable.
- Increases the risk of invalid inventory or price values.

## 4. Decision

We use resource-oriented REST-style endpoints and validate book data in the service layer before storing or updating records.

### Initial Endpoint Contract

| Method | Endpoint | Purpose | Expected success response |
|---|---|---|---|
| `GET` | `/books` | List books; optionally filter by title, author, or genre | `200 OK` |
| `GET` | `/books/:id` | Retrieve one book by ID | `200 OK` |
| `POST` | `/books` | Create a book | `201 Created` |
| `PUT` | `/books/:id` | Update book details while retaining the existing ID | `200 OK` |
| `PATCH` | `/books/:id/inventory` | Update inventory quantity | `200 OK` |

The root endpoint (`GET /`) provides a basic service status message and a list of available endpoint patterns.

### Book Data and Validation

The service validates the following fields:

- **ID:** Generated by the service for new records; an update must not replace the existing record's ID.
- **Title:** Required and must not be empty.
- **Authors:** Required as an array containing valid, non-empty author names.
- **ISBN:** Required and must not be empty.
- **Genre:** Required and must not be empty.
- **Price:** Must be a finite number greater than or equal to zero.
- **Publication year:** Must be an integer between 1 and the current year.
- **Inventory quantity:** Must be a non-negative integer.

Validation rules are applied in the service layer so they are not tied to a particular HTTP route.

### Error Responses

The initial API uses these status codes:

- `400 Bad Request` — the request contains invalid data.
- `404 Not Found` — the requested book does not exist.
- `500 Internal Server Error` — reserved for unexpected server failures.

Error responses include a JSON object with an `error` message where applicable.

### Inventory Updates

The inventory endpoint accepts a quantity that must be a non-negative integer. Negative values and fractional quantities are rejected.

The current implementation replaces the inventory quantity with the supplied quantity; it does not implement a stock-adjustment transaction or concurrent-update mechanism. Those capabilities can be evaluated if the service later requires persistent storage or concurrent inventory operations.

## 5. Consequences

### Positive Consequences

- Callers have a predictable set of endpoints and response codes.
- Invalid book records are rejected before storage.
- Inventory validation prevents negative and fractional quantities.
- Stable IDs allow clients to continue referring to a book after its details change.
- Automated tests can verify the contract and its error cases.

### Negative Consequences and Limitations

- Callers must follow the documented request structure and validation rules.
- The current API does not define pagination or sorting.
- ISBN uniqueness is not currently enforced.
- The API does not currently implement optimistic concurrency control or transactional inventory adjustments.
- The initial error format is simple and may need expansion if the API grows.

## 6. Implementation and Compliance

- Keep endpoint definitions in the routes layer.
- Keep HTTP request and response handling in the controllers.
- Keep catalog validation and business rules in the services layer.
- Return `400` for validation failures and `404` when the requested book is missing.
- Add automated tests when the API contract or validation rules change.
- Update the project README if endpoint paths, request formats, or response behavior change.

## 7. Review Triggers

Revisit this decision if the service adds pagination, sorting, ISBN uniqueness, more detailed error formats, concurrent inventory adjustments, or additional client requirements.

Any intentional change to the public API contract should be reflected in the README, automated tests, and relevant architectural documentation.
